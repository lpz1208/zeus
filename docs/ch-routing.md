# CH 收缩层级路由

`ch` 已接入 CLI、HTTP 路由、仿真车辆、Agent plan/commit、Python reactive Benchmark 和工作台选择器。它为基础静态道路费用构建索引，包含禁转、转向罚时及部分道路起终点；当前路况变化时明确回退至 `bidijkstra`。能力注册表将 CH 的 `supportsDynamicWeights` 标记为 false，回退行为由路由服务提供。

## 查询与预处理

以下索引适用于没有 via-way 序列的地图；含 via-way 时使用保留历史的 Dijkstra，见 [模型边界](via-way-routing.md)。没有转向规则时使用路口状态与道路弧；仅存在 edge-to-edge 转向规则时，每条有向道路对应一个“已进入该道路”的状态。相邻状态的转换费用为转向罚时加下一条道路完整费用；禁止转换没有对应弧。按潜在捷径数量减去移除弧数量的估计（权重 14），再加层级深度的确定性顺序收缩状态，见证搜索排除本次收缩的状态；只有找到费用不高于经过该状态路径的见证，才省略捷径。相同起终状态只保留费用最低的活动弧；旧弧记录仍供已有捷径展开。捷径保存不可变的两个子弧编号，查询结果迭代展开为原始道路序列。

查询从起点剩余道路费用出发；无转向规则时反向从目标入口路口及部分道路费用出发，有转向规则时则从该入口的每条合法入边及最后一次转向/部分道路费用出发。两侧沿层级上升，在最高状态相遇；两侧队列分别达到当前最优费用才停止，不能套用普通双向搜索的队首费用之和终止条件。同一道路上的直接路线由现有 RoutePlanner 比较。多起终点与 twin 语义保持不变。

设计参考：[Geisberger 等，Contraction Hierarchies: Faster and Simpler Hierarchical Routing in Road Networks](https://ae.iti.kit.edu/download/contract.pdf)。本实现采用有界见证搜索；未找到见证就保留捷径，搜索截断不牺牲最优性。

## 资源边界与复用

每个 RoutePlanner 按需构建一份只读索引，使用 `call_once` 发布，并发查询各自持有标签。Session Worker 内仿真初始化与 Agent 候选共享规划器，因此 CH 车辆初始化会先完成预处理。普通路由 Worker 与 Session Worker 的索引分别保存；没有磁盘预处理文件或跨进程共享。

默认资源参数：

- 最多 1,000,000 个状态（路口或进入道路）及 4,000,000 条弧（基础转换和捷径合计）；基础转换数量使用不扣除禁转的保守估计。基础图超过限制时不分配索引，回退至双向 Dijkstra。
- 每次见证搜索最多 settle 128 个状态；每个收缩点的入弧 × 出弧组合最多 65,536。
- 总见证搜索及相关弧扫描工作量预算 50,000,000。它是操作计数上限，不是墙上时间或精确内存限额；局部扫描和优先级更新也会产生开销。

收缩中达到预算时，丢弃当前尚未发布的整组捷径，保留该状态及其余未收缩状态作为核心图。查询在核心图内可双向搜索，仍然精确，`chCoreStates` 明确显示其规模。它可能比完整 CH 扩展更多状态，不将部分收缩视为完整收缩完成。

`chBytes` 统计保留的弧、层级、入出邻接数组及其 vector 容量，不包含分配器元数据、见证队列、排序集合、临时数组或查询标签。查询仍有 O(V) 或 O(E) 标签初始化及路径输出开销；有 overlay 时还要检查其是否完全恢复基础费用。首次预处理可能较慢，需要多次查询摊销。

## 动态路况与响应字段

有任一道路关闭或费用因子不等于 1，整次查询使用现有、限制感知的双向 Dijkstra，避免捷径掩盖封闭道路或使用过期费用。基础路况恢复后再次复用 CH。CH 不接收未来变速计划；这类查询仍应选择 `tddijkstra`。

成功响应保留 `algorithm: "ch"`，并返回真实 `effectiveAlgorithm`。新增字段：`chShortcuts`、`chCoreStates`、`chBytes`、`chPreprocessMs`、`chReused`、`fallbackReason`。CLI 使用 snake_case；HTTP 的部分零值字段可以省略，按 0 解释。

| fallbackReason | 含义 |
| --- | --- |
| 空或省略 | 本次实际执行 CH（可能含核心图） |
| `ch_dynamic_weights` | 当前路况不同于基础费用，改用 `bidijkstra` |
| `ch_base_graph_budget` | 基础状态或转换图超出限制，改用 `bidijkstra` |
| `via_way_history` | 地图有跨道路序列限制，改用保留历史的 `dijkstra` |

`chReused` 表示本次实际复用索引，动态回退时为 false；索引仍可以保留。`computeMs` 包含吸附、预处理（如有）及搜索，不含 HTTP 与 GeoJSON 输出。搜索扩展数按本次使用的路口或边状态累计，两侧分别统计。

## 精确提交与验收

CH 候选（包括回退产生的候选）保存精确道路序列；超过 9999 条道路拒绝提交。快照继续使用格式 3 / `zeus-session-replay-v3`，恢复不依赖预处理状态，索引在新进程内重建。

测试覆盖 600 组静态 CH 与 Dijkstra 对拍（各 300 组有/无转向规则）、600 组动态回退对拍、有向禁转/罚时、部分道路、twin、自环、不可达、完整及部分收缩、见证截断、捷径展开、恢复复用与 8 个并发首次查询。端到端脚本覆盖 HTTP 指标、封路回退、恢复 CH、多车复用、精确提交、跨服务重启、到达与六策略 Python Benchmark。

2026-09-26：临时路网和武汉地图完整端到端验收通过。武汉固定 OD `(114.4911555,30.9567005) → (114.4565038,30.9259153)`：268,670 条捷径、3,263 个核心状态、36,710,728 字节索引数组；首次预处理约 532.358 ms，复用查询 computeMs 约 0.153 ms。CH 扩展 17 个状态，对照 Dijkstra 79 个，费用均为 598.886 秒。临时小图上 CH 扩展数为 5、Dijkstra 为 3，因此不承诺所有路线都获得加速。这些是单次样例观测，不包含 HTTP P50/P95。

尚未实现可定制 CH（CCH）、时间依赖 CH、磁盘索引、跨进程共享、stall-on-demand 或分片预处理。加速效果需用固定 OD 矩阵测量，不能仅由单条路线的扩展数推断。
