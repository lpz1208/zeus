# 时间依赖路由

算法标识为 `tddijkstra`，注册表算法版本为 `1`，`supportsTimeDependency=true`。它根据出发时刻和已知道路变速事件求最早到达路径，以有向道路为搜索状态，保留禁转、转向罚时、精确部分道路起终点及 twin 端点语义。没有变速事件时退化为静态 Dijkstra。

## 时间模型

每条道路使用正的分段常数速度，穿越道路时按各时间段实际可行驶的距离累积；跨过变速时刻会继续以新速度行驶。事件前的速度因子为 1，最后一条事件持续生效。相同道路、相同时刻的事件按输入顺序处理，最后一条覆盖前面的值。速度因子范围为 `[0.05,3]`，允许减速与提速，拒绝零速、负数、非有限数和非法道路编号。

这样构造的到达函数满足 FIFO：沿同一条道路晚进入不会早驶出，因此可用按到达时间更新的 Dijkstra。算法依据参见 [Brian Dean：Shortest Paths in FIFO Time-Dependent Networks](https://people.computing.clemson.edu/~bcdean/paper23.html)。搜索不主动等待；转向罚时先加入到达路口的时刻，再计算下一条道路上的行驶过程。

`timeS` 表示本次出发到预测到达的耗时；`departureTimeSeconds` 和 `arrivalTimeSeconds` 是场景时间轴上的绝对秒数，不是现实日期。API 输出沿用三位小数，内部计算为双精度。

## HTTP 与 CLI

`POST /api/maps/{id}/route` 示例（道路编号需换成当前地图的有效编号）：

```json
{
  "fromLon": 114.0002,
  "fromLat": 30,
  "toLon": 114.0038,
  "toLat": 30,
  "algorithm": "tddijkstra",
  "departureTimeSeconds": 0,
  "speedChanges": [
    {"edgeId": 1, "timeSeconds": 5, "speedFactor": 0.1},
    {"edgeId": 1, "timeSeconds": 60, "speedFactor": 1}
  ],
  "recordTrace": true
}
```

HTTP 时间范围为 `[0,1e9]` 秒，最多 100,000 条变速记录，同时受既有请求体大小限制。非时间依赖算法携带变速记录或非零出发时间会被拒绝，避免静默忽略预测输入。

CLI 在普通 `route` 参数之外支持：

```sh
--algorithm tddijkstra --departure-time 0 --speed-changes '1,5,0.1;1,60,1'
```

路由 Worker 对时间依赖请求附加出发时刻和变速记录两个字段，仍接受原来的 9 字段请求。普通算法无需改变请求格式。

## 仿真、Agent 和工作台

- 原生仿真选择 `tddijkstra` 时，从现有 `roadControls` 的 `speedFactor` 事件构造预测。事件按仿真实际生效的 tick 向上对齐；原始时间不同但对齐后相同的事件仍按原始时间、稳定输入顺序生效。
- 首次规划使用车辆的请求出发时刻，并对齐至出发 tick。同一 OD、不同出发时刻分别缓存。途中重规划使用当前时间；未出发车辆使用当前时间与请求出发时刻中较晚者。
- 当前 overlay 的附加费用在一次查询中固定。对有速度事件的道路，先移除已发布的当前减速因子，再积分计划速度；保留的额外费用系数至少为 1。这是当前附加阻力的估计，不预测未来密度或容量变化。快照时间代表下一 tick 边界，已发布费用参考上一已提交 tick，避免恢复事件恰好生效时重复计算减速。
- Agent `/plan` 选择 `tddijkstra` 会自动读取该会话的道路变速事件，无需另传预测。候选按精确路径提交，最多 9,999 条道路；快照保存场景事件和已提交路径，重启后重建预测。沿用快照格式 3、重放契约 v3。
- Python Benchmark 的 `reactive` 策略可配置 `algorithm: "tddijkstra"`。这是使用已知场景计划的策略，比较指标时应区分其未来信息与只看当前状态的算法。
- 工作台的时间依赖路由预览增加“预览出发秒”，读取场景中的道路变速事件；变速事件或步长编辑后重新计算。预览出发时刻不修改仿真的车辆出发配置。

## 当前边界

最早到达的精确性仅针对上述速度函数、固定额外费用与静态转向罚时模型。真实仿真还包括离散 tick、车辆间隔、信号、排队、车辆自身速度控制和 hold/release，因此预测到达时刻不承诺等于实际到达时刻。

当前已关闭道路仍通过现有 overlay 禁入；正在道路上的车辆可以完成当前部分道路。未来 close/open、capacityFactor、路口管制、信号排队以及 hold/release 不纳入预测。未来事件实际发生时仍按原有失效通知、重新规划和 Action Guard 流程处理。尚未实现周期日历、非 FIFO 等待策略、到达时刻反向查询或交通状态预测。

当前实现逐次搜索，不保留跨请求的时间依赖标签，也未做 ALT/CH 加速。每次松弛先二分找到所处速度段，再扫描本次穿越涉及的后续段；事件非常密集时成本仍会增加。

## 验证

- 600 组无速度事件的冷启动查询与 Dijkstra 对拍，包括禁转、罚时、封路、twin 和部分道路。
- 120 组有变速、动态费用和禁转的随机有向无环路网，以“穷举路径 + 独立距离积分/二分求到达时刻”为参照，同时验证返回路径的成本。
- FIFO 跨恢复边界、相同道路部分行驶、变速跨段、重复事件、非法输入和静态算法拒绝预测输入。
- 原生仿真验证同一 OD 在不同出发时间选择不同路线，以及非整数事件的 tick 对齐和顺序。
- Go 验证协议精度、旧格式兼容、时间字段解析及非法预测拒绝。端到端脚本覆盖 HTTP 时刻差异、未出发 Agent 的恢复边界、精确提交、跨服务重启和到达，并将时间依赖算法加入 Python Benchmark。

2026-09-26 验收：`make test` 全部通过（C++ 三组、Go 全量、Web 类型检查及 11 项导航测试、Python 187 项）；前端生产构建通过。临时路网与武汉地图的完整端到端脚本均通过，包括 custom_code、reactive LPA*、reactive D* Lite、reactive 时间依赖路由四策略 Benchmark。测试中减速期间/恢复后出发的预测耗时分别为：临时路网 44.859/34.757 秒，武汉 OD 722.409/598.886 秒；这些是指定场景下的模型预测，不是计算性能指标或实际交通到达时间保证。恢复边界去重减速、未出发候选提交、跨服务重启、继续行驶到达均通过；旧导航、后台恢复与路线回切计数回归也通过。
